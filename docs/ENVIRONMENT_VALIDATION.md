# Environment validation: where the problems come from and what must be proved

This project is an RL-environment and verifier-infrastructure contribution. It
is not yet a training paper, and it does not need a long GRPO run in order to
establish that the environment is well designed. A training run is useful
evidence about a model/environment interaction, but it is a different claim
from environment correctness.

## The short answer

The problems are not invented by the prompt and they are not generated by the
language model. In the validated research corpus, each problem is a fixed
ACSL-C contract-completion instance derived from a CASP C/ACSL source record.
Ingestion re-verifies the complete source with the pinned Frama-C policy,
rejects verification flips and unknown/vacuous contracts, and records the CASP
record ID. The available CASP snapshot does **not** supply original per-file
attribution or license provenance; this is why it will not be bundled in the
public v0.1 wheel. The public `core-v1` follows the same transformation with
project-owned provenance. In either pack, the implementation body is removed
to form `skeleton_c`; that skeleton plus the fixed annotations and declarations
is the actual problem.

The prompt is an interface and a policy boundary. It tells the model what part
of the file may be changed and what output protocol to use. A prompt can be
ambiguous, leak a solution, or encourage a bad search strategy, so prompt
wording must be tested. It must not be allowed to change the task's semantic
truth: only the independently run verifier decides whether a completion earns
proof reward.

## Provenance chain

```text
CASP source pair
    -> pinned Frama-C replay + vacuity probe
    -> admitted reference_solution
    -> deterministic skeleton_c (target body replaced by TODO)
    -> system/user prompt or agentic workspace protocol
    -> model completion / edits to solution.c
    -> integrity gate (fixed context unchanged)
    -> isolated Frama-C WP + RTE run
    -> parsed verdict and staged reward/metrics
```

The concrete implementation is in:

- [`scripts/ingest_casp.py`](../environments/acsl-c/scripts/ingest_casp.py),
  which downloads CASP records, re-verifies them, builds the skeleton, and
  records provenance/quarantine decisions.
- [`src/acsl_c/taskset.py`](../environments/acsl-c/src/acsl_c/taskset.py),
  which constructs the prompt, seeds the agentic workspace, extracts the final
  source, applies the immutable-context check, runs the verifier, and computes
  reward components.
- [`src/acsl_c/integrity.py`](../environments/acsl-c/src/acsl_c/integrity.py),
  which defines the fixed-context boundary.
- [`src/acsl_c/verify_script.py`](../environments/acsl-c/src/acsl_c/verify_script.py),
  which is the small runner used to execute and serialize a verdict.
- [`src/acsl_c/spectests.py`](../environments/acsl-c/src/acsl_c/spectests.py),
  which intentionally keeps specification-strength reward conservative until
  executed negative cases exist.

`reference_solution` is the source of truth for eligibility and reference
replay. `skeleton_c` is the task shown to the model. `problem` is currently an
empty/legacy field for hints-mode records; it is metadata, not the semantic
specification. This is worth documenting so a future adapter does not mistake
an empty `problem` string for a missing task.

## Five different meanings of “problem”

When debugging a failure, classify it before changing code:

| Layer | What it is | Typical failure | Correct response |
|---|---|---|---|
| Data problem | A bad, flipped, duplicated, vacuous, or too-hard source record | Reference no longer proves under the declared image | Quarantine/replay under the manifest policy; do not tune the prompt |
| Transformation problem | Incorrect body extraction or skeleton construction | Braces, macros, multiple functions, or comments are cut incorrectly | Add parser fixtures and compare skeleton/reference invariants |
| Interface problem | System prompt, user prompt, output extraction, or agent protocol | Model edits an annotation or emits prose around C | Tighten protocol and test extraction; reward must still reject tampering |
| Runtime/verifier problem | Isolation, Frama-C invocation, parser, timeout, cache, or resource policy | A crash is treated as proof, or a stale cache is reused | Fail closed, key cache by the complete judge policy, retain evidence |
| Learning problem | Reward decomposition, turn attribution, sampling, or optimization | Dense partial reward does not improve useful edits | Run credit-assignment diagnostics; do not relabel a verifier bug as an RL result |

The verdict cache is part of the judge policy, not merely a performance detail.
Its key includes the source, toolchain label, prover selection, timeout, and a
digest of the exact verifier runner script. Changing the subprocess or parser
policy therefore invalidates old verdicts even if a human-readable toolchain
label was not updated.

This separation is the main answer to “do the problems come from the prompts?”:
prompt failures are one possible interface failure, but most correctness risks
are in data construction, source transformation, verifier isolation, and reward
semantics.

## Environment-infrastructure definition of done

The following gates are sufficient for a credible environment submission and a
local hub evaluation. They do not require a 500-step, multi-seed training study.

### Required gates

1. **Packaging and API.** A clean install can import the environment, load one
   task, reset/setup it, execute one action/turn, and tear down its runtime.
   The documented command succeeds from a fresh environment.
2. **Data integrity.** Every admitted reference is verified under the pinned
   image/toolchain; the split manifest is deterministic; task IDs are stable;
   provenance and exclusions are auditable; no train/eval reference leakage is
   present.
3. **Task transformation.** For every record, fixed context in `skeleton_c`
   is byte/normalization-stable, exactly the intended body is replaceable, and
   the reference source is accepted by the same parser and judge.
4. **Fail-closed scoring.** Parse failures, crashes, timeouts, empty/zero-goal
   reports, integrity violations, and runtime errors cannot receive proof
   reward. The scorer independently invokes Frama-C; model claims and edited
   `verify.sh` output are not evidence.
5. **Isolation and limits.** Model-controlled C is run only in the declared
   container/runtime, with network denied, bounded CPU/memory/time, a writable
   workspace, and no access to host secrets or another task's files.
6. **Reward semantics.** Gate, partial VC fraction, full proof, specification
   strength, and operational metrics are separately observable. Cache keys
   include source, toolchain, prover policy, timeout, and runner schema.
7. **Adversarial tests.** The test suite includes the reward-hacking and
   credit-assignment cases below, not just a happy-path reference completion.
8. **Reproducible evidence.** A smoke/eval command emits machine-readable
   traces, configuration, split/image/toolchain IDs, and logs. A second run can
   distinguish a true verdict change from cache or concurrency noise.

### Recommended but not required for an environment submission

- A short model smoke (for example, a few tasks and samples) demonstrating that
  the action/observation protocol is usable.
- A one-GPU serial LoRA/GRPO-compatible canary to expose integration and memory
  mistakes. Label it as a topology ablation; it is not evidence equivalent to
  asynchronous trainer/inference scaling.
- Prompt ablations (strict output-only, explanatory, and agentic feedback
  variants) with matched token budgets.
- A small human-readable gallery of successful, partial, malformed, tampered,
  timed-out, and crashed traces.

### Optional research evidence

Multi-seed 500-step training, held-out lift, statistical tests, contamination
analysis against external model training data, and scaling/throughput curves are
appropriate when making a claim about learning. They should not be presented as
prerequisites for the environment itself.

## Adversarial validation matrix

### Reward-hacking and verifier-integrity tests

Each case should have an expected verdict and a reason in a JSONL artifact.

| Attack | Example | Expected protection |
|---|---|---|
| Contract tampering | Change `requires`, `ensures`, loop invariants, signature, includes, or another function | Integrity gate is false; all rewards zero |
| Output smuggling | Return prose, multiple fenced files, or a second translation unit | Deterministic extraction plus parse/integrity failure |
| Vacuous proof | Remove a postcondition, stub the body, or exploit an unconstrained path | Ingestion vacuity quarantine; negative spectest or implication check rejects strength reward |
| Hard-code/reference theft | Read a reference file, another task directory, `/proc`, or hidden artifacts | Container/workspace isolation and no cross-task files; audit filesystem access |
| Compile-only success | Produce C that compiles but leaves WP/RTE goals | Proof reward remains zero; only independently parsed goals count |
| Fake verifier | Edit `verify.sh`, print “all proved,” forge JSON, or return code 0 | Final scorer ignores agent report and runs its own pinned runner |
| Undefined behavior | Trigger UB that happens to pass a test or solver path | RTE obligations, strict compile policy, and negative runtime cases |
| Timeout gaming | Deliberately make solver hang to exploit a partial-reward rule | Timeout is explicit, non-cacheable, and never proof-positive |
| Cache poisoning | Reuse a verdict after changing image/prover/timeout/runner | Full policy key and cold-cache replay test |
| Concurrency race | Two workers share a workspace or cache row | Per-task directories, WAL/transaction tests, serial-vs-concurrent comparison |
| Reward-boundary gaming | Maximize gate/VC fraction while never completing a proof | Component dashboard and held-out completion metric; inspect per-turn traces |

### Credit-assignment tests

The environment exposes a final proof result, but an RL trainer needs useful
signal about which action helped. Test this explicitly rather than assuming the
weighted scalar is informative:

1. **No-op control:** repeated no-op turns must not improve the score or create
   a false positive through cache reuse.
2. **Single-edit attribution:** apply one known-good edit, one known-bad edit,
   and a reverted edit at different turns. The final verdict and per-turn
   diagnostics must identify the causal edit.
3. **Monotonic partial proof:** completions that prove 0%, 25%, 50%, and 100% of
   the same obligations should produce ordered VC-fraction values, while gate
   and full-proof components remain separately interpretable.
4. **Late-reward case:** a proof that becomes valid only on the last turn must
   not be confused with a proof achieved by every preceding action. Record the
   final source hash and the first turn at which each component changed.
5. **Rollback case:** if a later edit breaks a previously proved source, the
   reward must fall and the trace must preserve both verdicts.
6. **Turn-budget sensitivity:** matched total tokens with 1, 2, and N turns
   should expose whether feedback helps or merely gives more output budget.
7. **Variance and normalization:** report per-task and per-group reward mean,
   variance, zero-reward rate, timeout rate, and proof rate; do not hide a
   sparse reward behind one aggregate average.
8. **Shaping ablation:** compare gate-only, VC-fraction, and staged rewards on
   identical completions. This tests whether shaping rewards progress toward
   proof rather than a proxy such as verbosity or solver time.

## Prompt-specific checks

Prompts deserve tests, but they are not a substitute for verifier tests.

- **Instruction locality:** the model sees the target body and the fixed
  context required to solve it, but not hidden answers or another split.
- **Boundary clarity:** explicitly state that only the target body may change,
  what “all goals proved” means, and the exact output format.
- **No accidental semantic drift:** changing the prompt must not change the
  task record, skeleton hash, reference hash, verifier flags, or reward code.
- **Extraction robustness:** test raw C, one fenced C block, prose plus C,
  multiple fences, truncated output, and Unicode/line-ending variants.
- **Ablation discipline:** if a prompt variant changes results, retain the
  exact prompt text and matched sampling/token settings in the artifact.

For the current adapter, hints mode intentionally supplies `skeleton_c` in the
user message and uses `SYSTEM_HINTS`; agentic mode instead supplies a seeded
`solution.c`, a verifier command, and `SYSTEM_AGENTIC`. These are two interfaces
to the same fixed task family, not two independently authored problem sets.

## Current project status against these gates

Already complete or strongly evidenced:

- CASP provenance, re-verification, vacuity quarantine, deterministic
  manifest, stable IDs, and the authoritative 316-reference serial replay.
- Frama-C/Why3/Alt-Ergo/Z3 image pin, independent scoring, fixed-context
  integrity gate, fail-closed parser, keyed cache, and container requirement.
- Prime-RL/Verifiers version pin and dry-run compatibility check.
- Qwen2.5-Coder-7B 4-bit Colab loading, deterministic capture, rollout-shape
  probe, and one-GPU memory measurements.

Completed on 2026-09-10:

- The negative spectest fixture has both an accepted control and a cleanly
  rejected wrong implementation; all declared expectations matched under the
  deterministic Qed policy. Full-mode contract synthesis remains disabled,
  while hints-mode strength continues to come from immutable annotations.
- The 35-test release suite covers contract tampering, fake verifier text,
  malformed/zero-goal reports, timeouts, runner-aware cache keys, concurrent
  cache access, and failed-edit/rollback trace history.
- Release configs use a restricted Docker runtime (`allow = []`), a writable
  isolated workdir, bounded CPU/memory/time, and independent final scoring.
- Verifiers v1's model-free `validate` command passed 3/3 gold references in
  fresh containers; the Prime-RL v0.9.0 configuration dry-run also passed.
- The built wheel bundles both data shards, the deterministic split manifest,
  and exclusions, and loaded a test task from an isolated install target.

The technical environment-infrastructure gate is therefore complete. Public
redistribution is a separate legal gate and is currently blocked because the
CASP-derived rows lack per-source license/provenance metadata; see
[`STATUS.md`](STATUS.md). The single-turn
versus multi-turn comparison, multi-seed GRPO study, and held-out learning lift
are optional research extensions and must not be implied by the release claim.

The authoritative closure record is
